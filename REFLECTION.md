# GroupWatch Reflection

## 1. Plan vs. Reality

The biggest gap between my original plan and what I shipped was not a missing feature. It was how well I followed my own feature boundaries. My [original feature loop](https://github.com/EEBarr14/GroupWatch/blob/0fa4e8e959de3a631db134bf93df8bbf4e2bd530/PLAN.md#L9-L24) says that every feature would have its own issue, branch, prompt log, pull request, merge, and deployment. It describes Library CRUD as adding, viewing, editing, and deleting a title. In reality, [PR #8](https://github.com/EEBarr14/GroupWatch/pull/8) also added an optional viewing service, the full password-recovery flow, and the line-art visual system.

The trail is visible in my [Library CRUD prompt log](./prompts/library-crud.md). The first prompt stayed focused: “Add a private, Supabase-backed library where a signed-in user can create a movie or TV show entry, view their library, open an entry's details, edit it, and delete it after confirming.” My follow-up changed the scope: “During visual review, add original continuous-line illustrations” and “also add a complete password recovery flow.” The recorded agent result says the finished branch included CRUD, viewing service, password recovery, and original line art. The PR description confirms the same result, including, “I also added the desert sunrise line art and carried the color palette through the landing, account, and library pages.”

This was my decision, not the agent quietly changing the project. I can tell because the extra work appears in my follow-up prompt. Once I could use the first version in a browser, the plain screens felt less personal, and password recovery felt important enough to address immediately. I decided to address the issue immediately and in the same branch, and directed the agent to do the same.

That decision resulted in a better, usable first version of my app, but muddied the clear vision I had laid out in the plan. PR #8 became harder to review because a database-backed CRUD flow, authentication behavior, and a visual system had to be checked together. Password recovery did not get its own issue and PR, so its history is less obvious. A bug in any one part would also have made the larger branch harder to diagnose. Later work went back to smaller branches, including the password-visibility fix in [PR #26](https://github.com/EEBarr14/GroupWatch/pull/26) and the connection-focused homepage in [PR #28](https://github.com/EEBarr14/GroupWatch/pull/28).

I would rewrite that part of the plan this way for a fresh agent:

> **Library CRUD:** Build only the private add, list, detail, edit, and confirmed-delete flow, including genre, watch status, and optional viewing service. Do not change authentication or add a site-wide illustration system on this branch. **Password recovery:** Build request-link and choose-new-password screens on a separate issue and branch. **Visual system:** Add the original group-watching line art and apply the desert palette across existing pages in its own design PR. If browser review suggests another feature, record it as a new issue instead of expanding the current branch.

That rewrite keeps the same product decisions while making the work easier to test, explain, and reverse.

## 2. The Stranger Test

I gave the live app to two family testers who are not in this class and are not especially comfortable with technology. They created and used their own account for about ten minutes while I watched. They operated the app themselves and asked questions when they were unsure instead of having me guide each click. That made the test useful because their questions showed where the interface was relying on assumptions I already understood as the person who built it.

Their first struggle happened around account access. They had forgotten their password, so they used the reset flow. The reset email and new-password process worked, but one tester wanted to reveal the password after typing it to make sure it was correct. Their second struggle was terminology. “TV Show” did not feel broad enough to them for every program on a streaming service, and they asked what to choose for something that was not a movie. “Series” would have been clearer. They also wanted more choices for where they were watching, including HBO, cable television, and “We Don't Remember.” Third, the public share page was understandable once they had the link, but finding the actual link was less obvious. After opening it, they expected to click a title to see my comments and wanted a way to have a conversation with me about it.

The clearest positive feedback was: “It was easy to figure out what the other person was watching once we had the link. Would be a nice thing for a family that is spread out like we are to stay connected by using.” That comment helped me understand that the strongest idea was not tracking for its own sake. It was using ordinary watching habits to maintain a relationship across distance. That directly influenced the connection-focused homepage in [PR #28](https://github.com/EEBarr14/GroupWatch/pull/28).

I chose password visibility as the problem to fix because it affected the front door to the whole app and could be solved safely without changing the data model. My [fix prompt](./prompts/password-visibility.md) says to add “Show password / Hide password” while keeping passwords masked by default and never including a password in evidence. [PR #26](https://github.com/EEBarr14/GroupWatch/pull/26) added one reusable password field to login, signup, new-password, and confirm-password screens. Browser testing also caught an accessibility problem where the toggle text became part of the input label, so I corrected that before merging.

I did not add public reviews or conversation. The public database function in [PR #22](https://github.com/EEBarr14/GroupWatch/pull/22) intentionally returns only a narrow set of fields. Exposing reviews would change that privacy promise, while a conversation feature would require accounts, permissions, moderation decisions, and probably notifications. I also left the terminology and extra viewing sources for a later usability pass. Those are valid improvements, but the password fix removed a more immediate barrier, and keeping the public page read-only was the right security and scope tradeoff before submission.
